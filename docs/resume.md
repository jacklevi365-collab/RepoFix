# 简历表述与投递前补充

项目的工程功能、离线验收和真实模型效果是不同证据。目前工程闭环已验收；DeepSeek 实际修复和策略对照尚未执行。以下工程描述可用于草拟项目经历，投递前应亲自跑通真实模型任务并能解释一次失败。

## 工程描述草稿

**RepoFix：基于执行反馈的 Python 代码修复 Agent**

技术栈：Python、DeepSeek Tool Calling、Docker、FastAPI、SQLite、SSE

- 实现仓库检索、按行读取、精确编辑与测试反馈的 Agent 执行闭环，提供 shell/结构化工具及 full/compact 上下文策略，记录 token、耗时、成本与完整执行轨迹。
- 设计原始失败复现、独立测试、原有用例回归及测试完整性门禁，在冻结代码的干净副本中验证补丁；建立 5 个人工开发任务和 3 个带来源、许可证与源码指纹的开源历史回归任务。
- 基于 FastAPI 和 SQLite 实现异步任务队列、SSE 事件续读、幂等提交与产物下载，结合事务预算预留和原子轮次检查点，控制请求成本并避免不明状态下重复执行。

这三点描述实现与系统设计，不包含模型成功率或优化收益。第三方基准源码属于 more-itertools，贡献在任务整理、验证与系统实现，不应把上游代码量写成个人开发量。

## 实测后再补充的表述

真实结果产生后，用报告中的精确数值替换下面占位符；没有证据的句子直接删除：

> 在固定的 N 个公开历史回归任务上完成 X 个修复，候选补丁均经独立用例与指定原有回归验证；在相同模型、步数与预算下，对比四种工具/上下文配置，记录每任务 token、费用、耗时和失败原因。

如只有当前三个同库公开历史任务，优先写 X/3 并说明范围，不外推为通用修复能力；参考补丁通过率不能替换 Agent 成功率。单轮实验也不足以声称成本或成功率普遍改善。

## 投递前的个人验收

1. 能不看文档启动服务，展示一份真实模型产生的 diff 和测试结果。
2. 能指出模型决策、工具执行、控制器门禁各自负责什么。
3. 能解释一个失败案例，并从轨迹定位原因。
4. 能用固定配置重跑一个任务，说明预算、停止条件和数据来源。
5. 能讲清检查点为什么只在安全轮次恢复，以及哪些状态拒绝自动重放。
